`useFleetbase().adapter` from `@fleetbase/sdk`). Edits to existing files are in `PATCHES.md`. SPEC.md was followed: driver REST under `/v1/service-tracker/*` (the SDK adapter supplies host + `v1`,

## Offline queue behaviour (all covered by tests)

* Persisted write-through to MMKV on every change; FIFO by sequence; survives restart (in-flight items are simply re-sent).
* **Records** are strict FIFO. A network/5xx/408/429 failure at the head halts the record lane and retries with exponential backoff (2 s base, x2, 5 min cap, +<=20 % jitter; clock/random/scheduler injectable).
  Plain offline never parks an item; 10 consecutive 5xx responses park it as "failed" (visible in the banner with Retry / Discard). 4xx other than 401/408/409/425/429 parks immediately without blocking the rest. 409 = "already have it" = delivered. 401 pauses without burning attempts (`resumeAuth()`).
* **Photos** are a separate lane: never block records, never roll them back, wait for their parent record, retry independently. Dependants of a rejected parent are parked too.
* **De-dupe**: enqueue of an existing or already-delivered `client_uuid` is a no-op; a lost response (server applied, client saw an error) resends the same `client_uuid`, which the server must answer idempotently (SPEC).
* **Offline-created parents**: later writes reference `{{ref:<client_uuid>}}` in path/body/fields; resolved to the server id returned for that `client_uuid` (ledger of the last 5000 persisted).
* Vendor-stop stamps carry `at` = the device time of the tap, not of delivery.

## Assumptions on the REST API (confirm with the PHP/API agent)

1. List/detail visits accept `with=stops,jobs,damage_records` and return nested snake_case objects; entities echo `client_uuid`; ids returned are **public ids** (`visit_xxx`) and are accepted in paths and in `service_visit_id`. Response is either an array or `{data:[...]}` (both handled); creates return `{data:{id}}` or `{id}` (`public_id` preferred).
2. Writes used: `POST visits`, `PUT visits/{id}`, `POST visits/{id}/stops`, `POST visits/{id}/stops/{stop}/{check-in|approval-requested|approval-received|left}` body `{at, client_uuid}`, `POST visits/{id}/jobs`, `PUT service-jobs/{id}`, `POST damage-records`, `POST petty-cash` (amount in integer halalas, `currency`), `POST uploads` (multipart: `photos[0]`, `client_uuid`, `subject_type` = `visit|damage|petty_cash`, `subject_id`, plus `stage` = `pickup|return` and `angle` for inspections). SPEC does not define upload subject parameters: **these names are my assumption**.
3. SPEC lists no driver `settings` endpoint. The app calls `GET service-tracker/settings` (dropdown lists: damageLocations, damageTypes, severities, expenseCats, svcStatuses, vendors, currency) and silently falls back to the defaults from `defaultSettings()` in Index.html when it is missing. A driver-visible subset of settings should be exposed (or embedded in `catalog`/`lanes`).
4. `GET vehicles/due` returns `[{plate, make_model, last_odometer, items:[{service_name, next_due_km, km_left, status?}]}]`. `status` is optional; otherwise derived from `km_left` (<0 overdue, <=1000 due soon).
5. `GET catalog` returns `{id, name, category, lane, suggested_vendor_name, interval_km}`.
6. `PATCH` is not used (the app's SDK 1.x adapter may lack it); `fleetbaseTransport` falls back to `put` if `patch` is missing anyway.

## Unverified here

* **Nothing React Native was run or built** (no device/simulator, no Metro, no Fleetbase backend). Screens were only type-checked with `any`-typed stand-ins for `tamagui`, `@fortawesome/*`, `@gorhom/*`, `react-native-fs`, the resizer and `react-native-safe-area-context`; prop names on those (e.g. tamagui tokens like `$warning`, `$warningBorder`, `$successBorder` that I saw in `tamagui.config.ts` only for `warning*`, `error*`, `info*`, `success*` via other components) and visual layout/RTL appearance are unchecked.
* Behaviour of the real `@fleetbase/sdk` ^1.2.13 adapter: error object shape (`status` / `response.status`), multipart posting of React Native `{uri,name,type}` parts through `adapter.post(..., { headers })` (copied from `ProofOfDeliveryScreen`), and whether network failures surface without a status. Misclassification here would turn offline errors into "parked" items; `statusOf()` in `fleetbaseTransport.ts` is the single place to adjust.
* MMKV v4 API as exported by the app (`storage.getString/set/remove`): taken from reading `use-storage.ts`, not executed.
* `CameraCapture` (vision-camera) integration: it returns `[{uri}]`; Inspection maps them onto angle slots. Resizing (`@bam.tech/react-native-image-resizer` with `onlyScaleDown`) and `react-native-fs` copy are untested on device; output size/quality were not measured (only the target-size maths is unit tested).
* `BottomSheetSelect` / `MoneyInput` behaviour inside my screens (portal hosts `CreateDamagePortal` / `CreatePettyCashPortal`, `scrollEnabled` toggling while a sheet is open) mirrors `FuelReportForm` but is unexercised. `MoneyInput` never emits a cleared amount (see PATCHES.md section 6); I show "Will be saved as ..." to expose that.
* `OdometerNumber` currently renders `0` for any truthy value (existing bug, PATCHES.md section 6), so odometer digits will be wrong until that one line is fixed.
* NetInfo wiring (optional dependency) and AppState/30 s polling were not exercised.
* Arabic strings were written by me, not reviewed by a native speaker (please have the ops team check the damage/inspection wording). RTL: text follows the locale, but I do **not** call `I18nManager.forceRTL`; row direction only flips if the app/OS already runs in RTL (changing it needs an app restart, so that is a product decision). Vendor/category/location values stay English on the wire (they are data); only their display is translated where a translation exists.
* Server-side `calc` (when present on a visit) overrides the local stage maths for non-pending visits; the local port covers stages/total/target only. Overdue-service counts shown in the visit list come from `visit.calc.overdueN` and are blank offline or when the API omits them.
* No real-time sockets/push were added; data refreshes on open, pull-to-refresh, foreground, and after the queue drains.
* Not handled: editing/deleting damage or petty-cash after creation, deleting a stop, multi-device conflict resolution beyond "server wins on refresh while no local change is pending".
